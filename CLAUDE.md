# REDcode: notes for Claude sessions

REDcode is a Cyberpunk 2077 modding IDE built on VS Code, wrapping WolvenKit's C# engine behind a local JSON-RPC bridge. It is the build-time half of the ecosystem; REDnode (https://github.com/Edgemodders/REDnode) is the runtime half. The same person owns both, and REDnode's `CLAUDE.md` and `docs/dev-setup.md` set the conventions used here too.

## Current status and next step

- **Requests from other repos:** open issues labelled `request` at https://github.com/Edgemodders/REDcode/issues?q=is%3Aissue+is%3Aopen+label%3Arequest are needs from EDGEbuilder and REDdeck, each with the shape that would work. Read them at the start of a session and pick them up when the current phase is done; close each with a note on what shipped.
- **Design:** `docs/design.html` (draft 0.1, checked in 2026-10-11, also published at https://edgemodders.github.io/REDcode/design.html). It is the architecture document: decisions, bridge protocol, feature map, layout, roadmap. It fixes the shape of each feature in a line or two; anything bigger than a command, such as the CR2W editor, gets its own short design page under `docs/design/` agreed in chat before code.
- **License model (decided):** split. This repo stays MIT and holds the extensions and, later, the branded fork. The bridge lives in its own repo, REDbridge (https://github.com/Edgemodders/REDbridge), under GPL-3.0 because it links WolvenKit's GPL-3.0 libraries. Extensions talk to the bridge only over stdio with JSON-RPC and never link it in-process. Keep that boundary.
- **In the repo:** `extensions/redcode-core` (C2 done: the REDcode activity bar container with a Project view over WolvenKit `.cpmodproj` projects and a Game Assets tree over the archives; new project, add to project, extract to, open game or project files as JSON) and the shared theme. F5 runs the extension; `npm run smoke` in `extensions/redcode-core` drives the bridge client without VS Code. Project files are WolvenKit's XML (`CP77Mod`) with the `source/archive`, `source/raw`, `source/resources`, `packed` layout; keep them byte-compatible.
- **C3 so far (2026-10-11):** Save JSON to Project (edit a project file as JSON, rebuild it through `cr2w.fromJson`), the texture viewer (`.xbm` custom editor and panel over `texture.toPng` and `texture.fileToPng`, bridge 0.3.0), and TweakXL language support (`.tweak` grammar, configuration, snippets, `samples/example.tweak`). Core is 0.3.0; `MinBridgeVersion` stays 0.2.0 and the viewer explains itself on an older bridge.

Still to do for S1: the `redcode.pack` command (progress, log, warnings notification, Project view refresh and reveal of the archive), a `redcode` task provider with `pack` as a build task (CustomExecution and a pseudoterminal writing the log lines), settings `redcode.pack.clean` (true) and `redcode.pack.redmod` (false), a smoke step that packs the extracted files and reads them back with `openMod`, README and CHANGELOG, then the owner's hand test on TestMod against a WolvenKit pack of the same project. The user's running bridge locks its exe: build the bridge into a scratch folder with `-o` to test, and let the owner run REDcode: Update bridge for the real one. Keep `bridgeClient.ts` free of VS Code imports.
- **Bridge install and update (2026-10-13):** `src/bridgeUpdater.ts` (no VS Code imports) plus `updateBridge` in `extension.ts`. Install bridge downloads the latest GitHub release (`redcode.bridgeRepository`) under global storage and sets `redcode.bridgePath`; Update bridge does the same, or runs `npm run update` when the exe sits in a git checkout. The bridge is stopped with `stopAndWait` first because the running exe locks its own file. A missing .NET 10 runtime is detected with `dotnet --list-runtimes` after a failed start and winget is offered. Hand-tested by the owner on 2026-10-13: checkout update 0.5.0 to 0.5.1, release install, and the already-latest case. Install bridge overwrites `redcode.bridgePath`, so note the old value first when switching back.
- **MCP server (2026-10-12):** `packages/redcode-mcp` exposes every bridge method as MCP tools over stdio for assistants (Claude Code, REDagent); it bundles `bridgeClient.ts` from the extension source, which is why that file stays free of VS Code imports. Build with `npm run mcp:build`; test with an MCP client against the game, not by hand. Docs: `docs/mcp.md`.
- **C0 findings (2026-10-11):** the Redscript IDE extension is `jac3km4.redscript-ide-vscode` on the Microsoft Marketplace and is **not** on Open VSX, so the branded fork (C7) must either bundle it with the author's permission or depend on it being published there. The WolvenKit team will be contacted once a working proof of concept exists, not before. The .NET side of C0 (building WolvenKit's libraries) is tracked in REDbridge.

## Conventions

- Commit straight to `main` and push, in small logical commits. Agree the plan in chat first. PRs only for large or risky changes.
- Git identity is set per repo to `CyberbuildsAI` with the GitHub no-reply email. Never change the global identity.
- Never commit game files, WolvenKit binaries, or data extracted from the game.
- Record every tool install in a `docs/dev-setup.md`, with versions and exact commands.
- Writing style: plain, short sentences, tables for comparisons. Terms: the bridge (`REDcode.Bridge`), extensions `redcode-core`, `redcode-explorer`, `redcode-editors`, `redcode-tools`, phases C0 to C7. Mark anything unverified as unverified.
- House style is the HUD look from REDnode's design doc. The `rednode-hud-theme` extension is the default theme. Keep its package identity `edgemodders.rednode-hud-theme` (publisher `edgemodders` since 2026-10-12; it was `cyberbuildsai`). This is the theme's only home since 2026-10-11; REDnode's copy was removed, so edit it here only.
- Goal to keep in mind: an AI-first, Node-based ecosystem. Claude is the first assistant it is built with; the stack is JavaScript/TypeScript, npm packages, HTML views and VS Code. Prefer machine-readable interfaces (JSON-RPC, generated types, structured docs), and plan for the bridge to double as an MCP server. Coexist with WolvenKit and credit it.
- REDcode and REDnode form one loop: edit a REDnode mod in REDcode (with an assistant), deploy it to the running REDnode process without restarting the game, and stream the game's events and logs back. This lives in a `redcode-rednode` extension and needs a development endpoint on the REDnode side. Live debugging is part of it: VS Code's debugger attaches to the REDnode process over the Node inspector (breakpoints, Debug Console against the live game); Tier 1 interceptors in QuickJS get trace and replay instead.

## Docs site

- `docs/` is published by GitHub Pages at https://edgemodders.github.io/REDcode/ through `.github/workflows/pages.yml`. Settings > Pages > Source must be GitHub Actions.
- Write docs as markdown in `docs/`. Jekyll renders them with the HUD layout (`docs/_layouts/default.html`, `docs/assets/css/hud.css`). Add every new page to `nav` in `docs/_config.yml`.
- `tools/brand/render.ps1` regenerates the banner, social preview, icon and badges. Re-run it when versions in the badges change.
- When the first extension has TypeScript, add TypeDoc to the Pages workflow the way REDnode does, so the API reference is generated.
