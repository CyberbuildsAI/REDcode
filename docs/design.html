// Research & architecture

REDcode

A Cyberpunk 2077 modding IDE built on VS Code. It takes WolvenKit's capabilities, the archive browser, the CR2W file editors, import and export, and project packing, and delivers them as VS Code extensions, with WolvenKit's own C# engine doing the file work behind a local bridge process.

Recommended: extensions first, branded fork later Engine: WolvenKit C# behind a JSON-RPC bridge Open: license model AI-first: JS/TS, npm, web, VS Code, Claude Companion to REDnode

01Goal and scope

In scope
  • A VS Code based IDE for Cyberpunk 2077 asset modding that covers WolvenKit's main workflows: browse game archives, add files to a project, edit CR2W files, import and export assets, pack a mod.
  • WolvenKit project compatibility: open and build existing .cpmodproj projects.
  • A layout that resembles WolvenKit's, within what VS Code allows.
  • A path from "extension pack on stock VS Code" to "branded REDcode application".
Out of scope for v1
  • Rewriting WolvenKit's file parsers. The C# engine is reused.
  • Parity with every WolvenKit editor. Graph editors, ink widget preview and layered material preview come last.
  • Linux and macOS. WolvenKit's texture tooling is Windows-only and the game is Windows.
  • Script compilation and language support for redscript. The existing Redscript IDE extension covers that and is reused.

Relation to REDnode

REDnode is runtime scripting: a Node API that talks to the running game. REDcode is build-time tooling: files, archives and projects. They share the HUD house style, and the REDnode HUD VS Code theme is REDcode's default theme. The two are meant to work as one loop: a REDnode mod is edited in REDcode, deployed to the running REDnode process without restarting the game, and the game's events and logs stream back into REDcode. A redcode-rednode extension carries this: project scaffolding, generated types, a run task, a deploy command and a live event view.

02AI-first ecosystem

REDcode and REDnode exist to offer a modding ecosystem that works with AI assistants as well as it works with people. The stack is chosen for that: JavaScript and TypeScript, Node and npm, HTML for every view, VS Code as the shell, and Claude as the first assistant it is built with. These choices shape the design more than feature parity with existing tools does.

Everything is text a model can read and write

Game files as CR2W JSON, tweaks as YAML, scripts as redscript and JavaScript, projects as folders. No state lives only inside a GUI. Whatever a person can see in REDcode, an assistant can read, and whatever a person can change, an assistant can change through the same files and calls.

One API, two clients

The bridge's JSON-RPC methods serve the VS Code extensions and an MCP server alike. An assistant such as Claude Code can browse archives, convert files, query TweakDB, run scripts and pack a mod through the same calls, while REDcode stays the person's view of the same project.

npm is the package format

Mod tooling, scripts and shared code are npm packages. The wkit-compatible scripting API ships as a typed package, so existing community scripts become packages and new ones get completion and documentation for free, for people and for assistants.

The live loop with REDnode

An assistant working in REDcode edits a REDnode mod, REDcode deploys it to the REDnode process attached to the running game, the change takes effect at once, and the game's events and logs stream back into REDcode. The assistant sees the result and iterates. Tier 2 mods reload freely because they run outside the game; Tier 1 interceptors swap between frames. Asset changes that the game cannot reload while running are marked as needing a restart.

The same process is debuggable live. REDnode's Tier 2 is an ordinary Node process, so VS Code's built-in debugger attaches to it: breakpoints, stepping and watches in the TypeScript source, and a Debug Console that evaluates calls such as await game.player.getHealth() against the running game. Tier 1 interceptors run in QuickJS inside the game, which has no inspector, so they get tracing and replay: inputs and outputs are recorded and the interceptor is re-run in Node under the debugger.

Web views, generated references

Every viewer is HTML, so it can be reused in the docs site, in previews an assistant produces, and in the branded fork. API references for the bridge, the scripting API and the game types are generated from source and RTTI, shared with REDnode's docs site, and readable by assistants as well as people.

Native dependencies
  • kraken.dll: Oodle decompression. Has Windows, Linux and macOS code paths.
  • texconv.dll, DirectXTexNet: texture conversion. Windows-only.
  • wwtools.dll: Wwise audio.
  • Assimp: mesh import.
CLI commands

archive, unbundle, uncook, import, export, pack, build, convert, conflicts, hash, oodle, settings, wwise. convert turns CR2W files into JSON and back, and --print writes the JSON to stdout.

Built-in scripting

WolvenKit embeds V8 (ClearScript) and exposes a wkit API of about 44 functions to user scripts: load and save project files, get files from archives by path or hash, export, query TweakDB, hash strings, open documents. Five hooks: onSave, onExport, onPreImport, onImportFromJson, onParsingError.

Why the scripting API matters

WolvenKit already has a UI-independent, JSON-shaped API designed to be called from JavaScript. It is close to the contract REDcode's bridge needs, and the community has scripts written against it. The bridge should offer the same surface, so those scripts keep working. One caveat: that API lives in WolvenKit.App and reaches into WPF view models, so the bridge reimplements it over the headless libraries rather than referencing WolvenKit.App.

Data formats

  • CR2W JSON. RedJsonSerializer writes { Header, Data: { RootChunk, EmbeddedFiles } }. Every editor in REDcode works on this shape.
  • Project. A .cpmodproj file next to source/archive, source/raw, source/resources and packed/. Per-project layout.xml stores WolvenKit's panel layout.
  • File types. About 150 extensions in ERedExtension, from mesh, xbm, ent and app to streamingsector, scene and inkwidget.

Recommendation

Build everything as extensions (A) and treat the branded fork (B) as a packaging step at the end. B is A plus a product.json and a build pipeline. Nothing in the extensions changes between the two, so the fork can wait until the extensions are worth shipping.

Marketplace rule

Microsoft's Marketplace terms limit its use to Microsoft's own products. Forks such as VSCodium and Cursor point at Open VSX instead. A REDcode fork would do the same, and the REDcode extensions would be published to both registries. The exact wording of the current terms was reported second-hand in research and should be read directly before the fork ships. Checked on 2026-10-11: the Redscript IDE extension (jac3km4.redscript-ide-vscode) is on the Marketplace only, not on Open VSX, so the fork must bundle it with its author's permission or depend on it being published there.

05Decision 2: port or wrap

OptionApproachStrengthsWeaknesses
PortRewrite the parsers and tools in TypeScript.Single language. No .NET runtime to ship. Could run anywhere VS Code runs.685,000 lines in RED4 alone, most of it generated type definitions that would need regenerating from the game's RTTI. Oodle, DirectXTex and Wwise are native and would need WebAssembly or native Node modules. Years of work before parity. Translating GPL source is a derivative work.
WrapRun WolvenKit's headless libraries in a separate .NET process. Extensions send requests and render the results.All format support on day one, and it tracks WolvenKit's updates. The UI is the only thing to build, which is true in every option because the WPF layer is not reusable.Ships a .NET runtime (about 80 to 100 MB self-contained). Windows-only until the native libraries are. WolvenKit has no stable public API, so the bridge pins a version.
HybridWrap for formats, port what is cheap and benefits from being native in VS Code.This is what "wrap" becomes in practice. The project model, hashing, YAML and redscript editing, file watching and all UI live in TypeScript. CR2W, archives, Oodle, textures, meshes, audio and TweakDB stay in C#.
Key observation

Whether REDcode ports or wraps, the UI is rebuilt. WolvenKit's views are WPF on a commercial control suite (Syncfusion) and a WPF 3D engine. None of that transfers to a web-based editor. The port-or-wrap question is only about the engine, and wrapping keeps 730,000 lines of working, maintained code.

Design rules

  • Partial reads for big files. A streaming sector can produce hundreds of megabytes of JSON. The CR2W editor loads the chunk tree lazily with cr2w.getChunk and sends edits as patches, rather than round-tripping whole documents.
  • Files for bulk data. Decoded textures, glTF meshes and WAV audio go to a per-workspace cache folder. RPC carries paths, not bytes.
  • Game path once. The bridge loads the archive index at start from the configured game folder, the same setting the Redscript IDE extension uses.
  • Crash isolation. If the bridge dies, the extension restarts it and the editors reconnect. VS Code never freezes on a bad file.
  • Distribution. The bridge is published self-contained for win-x64. The extension pack downloads it on first run and verifies a checksum. The branded fork bundles it.

09Licensing and the name

Not legal advice

These are the known constraints and the usual readings of them. Have someone qualified confirm before a public release, and talk to the WolvenKit team early. The modding community is small and a tool seen as a hostile clone would struggle.

WolvenKit is GPL-3.0
  • A bridge process that links WolvenKit's assemblies is a derivative work and must be GPL-3.0.
  • A VS Code extension that only talks to that process over stdio, exchanging data, is usually treated as a separate program and can keep its own license.
  • Porting by reading and translating WolvenKit source produces a derivative too. Only a clean-room port from the game's RTTI and public format documentation could be MIT.
Two license models
  • Split. Bridge in its own GPL-3.0 repository. Extensions and fork in the MIT REDcode repository. Clean, but two repos and a boundary to police.
  • All GPL-3.0. One repository, no boundary, and goodwill with upstream. Costs nothing unless REDcode must be MIT for another reason.
Other components
  • Syncfusion controls: commercial, community-licensed to WolvenKit. Not reused, so irrelevant.
  • kraken.dll (Oodle): WolvenKit redistributes it. Its origin and license need checking before REDcode redistributes it too.
  • No game files or data extracted from them go in any repository. Same rule as REDnode.
The name

REDcode is RED for REDengine and code for VS Code, the editor it is built on. It was chosen on 2026-10-11 after checking three places. CD Projekt RED uses REDengine, REDmod, REDlauncher and REDcode, not REDcode. No Cyberpunk modding tool uses it. Outside modding, RED Digital Cinema's REDCODE RAW video codec and Core War's Redcode language share the spelling; both are different products in different fields and were accepted. A trademark search by someone qualified is still worth doing before the branded fork ships.

11Roadmap

C0DECIDE

Decisions and groundwork

Name and license model: done (REDcode, split model with REDbridge under GPL-3.0). Redscript IDE on Open VSX: checked, it is not. Remaining: build WolvenKit's headless libraries locally and confirm Code - OSS builds on the reference machine. The WolvenKit team is contacted once a working proof of concept exists.

C1BRIDGE

Bridge MVP

A .NET bridge with archive.list, cr2w.toJson, cr2w.fromJson, texture.toPng and hash.*. A VS Code extension that spawns it and offers "Open game file as JSON". Proves the data path end to end.

C2BROWSE

Project and asset browser

Open a .cpmodproj. Project Explorer, Asset Browser with search, add to project, extract, Log channel, status bar. REDcode becomes useful for browsing and extracting.

C3EDIT

Core editors

The CR2W custom editor with chunk tree, properties and patches. Texture viewer. TweakXL language support. Undo, redo, dirty state and save back to CR2W.

C4SHIP

Import, export, pack

Import and export over Modkit with a settings webview. Pack and build tasks. First mod built start to finish inside REDcode. Publish the extension pack.

C5VIEW

Mesh, audio, TweakDB, scripts

3D viewer over glTF. Audio player. Tweak and LocKey browsers. wkit-compatible script runner with typings, published as an npm package. MCP server over the bridge, so assistants can work a project alongside REDcode. REDnode integration: scaffold, generated types, deploy to the running REDnode process, events and logs streamed back, debugger attached with a live Debug Console, trace and replay for interceptors.

C6PARITY

Graphs and previews

Graph editors for quest, scene and behavior files. Ink widget preview. Layered material preview. Ordered by what modders ask for.

C7BRAND

Branded fork

Code - OSS build with product.json: REDcode name and icon, REDnode HUD theme as default, bundled extensions and bridge, Open VSX registry. Installer and release pipeline.

12Open questions

  • License model: split (MIT extensions, GPL bridge) or all GPL-3.0?
  • Which file types do you mod most? That orders C3 to C6.
  • Is Windows-only acceptable for v1?
  • Should the bridge be a hosted copy of WolvenKit's libraries, or should the bridge host be contributed upstream so WolvenKit ships it?
  • Should REDcode also carry REDnode project support (scaffold, types, run task), or stay purely asset tooling?
